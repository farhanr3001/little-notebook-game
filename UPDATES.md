# Native installation and differential updates

The installer is per-user, at `%LOCALAPPDATA%\Programs\Little Notebook`, with saved state at `%LOCALAPPDATA%\LittleNotebook`. `installed.ini` identifies the product, version and data directory. Installed app files and data are separate; neither release packs nor installer payload contain profiles.

`Updates.cs` reads the latest public GitHub release for farhanr3001/little-notebook-game, compares the compiled AppInfo version and retrieves update-manifest.json only for a newer version. Offline/error results are quiet on startup and explicit when Check for updates was requested. A current version shows no startup update popup. Later dismisses only the current notification; a subsequent launch still offers the update.

The manifest has version/repository/notes, files (relative path, size, SHA-256, component pack), and packs (release URL, size, SHA-256). The client compares installed bytes, downloads only packs containing required changes, verifies archive/file hashes, and extracts only changed files into the data directory's updates staging area. Components avoid repeatedly downloading unchanged voices or music. A component can contain unchanged files; those are neither extracted nor rewritten.

The native updater runs from staging after the parent exits. It validates the product marker, staging/data root and every managed path, rejects traversal, user-data paths and directory links, verifies staged hashes, makes rollback copies, and atomically replaces only changed/new files. Removed formerly managed files are handled separately. It updates the local manifest/version and restarts the game. It never invokes Setup during an in-app update. On failure it restores previously changed files where possible; saved data is outside this transaction.

The manifest is delivered over HTTPS from the explicitly configured GitHub repository. No GitHub token is shipped in the client. Release assets should be published as a draft and made public only after all packs and the manifest are present. An unsigned public-release pipeline relies on the security of the GitHub account/repository; a future signing certificate could add publisher authentication.

For a new release, bump AppInfo.Version and assembly/app manifest versions, build, run only checks relevant to the changes, run build_release.py with the new source/version, compile the installer with `/DAppVersion=...`, and publish installer + update-manifest.json + every update-packs ZIP. The GitHub workflow provides the same process. Keep the product ID and data directory stable. New managed top-level directories must be explicitly allowed in UpdateFiles.SafePath and the uninstaller.

Uninstall uses the latest managed manifest, so it also removes files introduced by updates, then removes app-owned payload/data directories and registered shortcuts/registry. Deletion targets are fixed product locations checked against the product marker. It does not search drives for old source workspaces or delete exported user images.

Tests use `/TESTINSTALL=1` and a workspace `/DIR=...`, which creates a separate uninstall identity and data directory under that isolated app root. `--apply-test` is accepted only for this isolated data root. test_install_update.py checks fresh install, changed/new files, unchanged timestamps, byte-identical state/imports, locked-file rollback, hash rejection and uninstall cleanup. Never point those tests at the normal data directory.

Setup includes the signed Microsoft .NET Framework 4.8 and Visual C++ x64 offline installers and detects installed versions before running them. Missing shared prerequisites may require Windows elevation; a required restart is reported and post-install game launch is skipped until then. Python and voices are private bundled files. Uninstall retains shared Microsoft prerequisites used by other applications.
